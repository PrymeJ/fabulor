## Theme system

- **`MainWindow._set_bg_suppressed` is a live, deliberate bypass of the `_apply_stylesheets` dispatcher — hover-safe since `0439c76`, but uninstrumented** (2026-07-20, re-verified 2026-08-02) — `app.py:1502` calls `content_container.setStyleSheet()` directly on every book-load and empty-state transition, on a call graph with **no coupling to ThemeManager's fade/hover state machine**. The hover-bleed danger is closed (it now reads through `get_active_theme()` rather than the raw field), and the bypass itself is a deliberate design choice documented at the call site (avoiding a flash to the non-cover theme). What is NOT known is its cost: the 2026-08-02 restyle measurements instrumented only `_apply_stylesheets` call sites and never counted this one. Likely cheap (~20ms, extrapolating from the `title_bar + content_container` step) but it fires on a hot path and should be measured before any per-call restyle inventory is treated as complete. Full call-site inventory in **`review/Audit_260720_theme_reach.md` §1** — that audit's own bug findings (Paths A and D) are both FIXED and should not be re-investigated, but §1 remains current and is the best starting point for the Stats perf session.
- **Every theme operation pays ~550ms because ANY `mw.setStyleSheet()` call re-polishes the whole tree — content is irrelevant and DEPTH is the multiplier** (2026-08-02) — measured against the real `MainWindow` (632 descendants): the full 27-rule base sheet (768ms), a **single** `QWidget#mainwindow` rule (850ms), an **identical** re-set of the current sheet (547ms) and an **empty** string (543ms) all cost the same. Qt does not no-op an identical sheet, and clearing is as expensive as setting. This **kills two options outright**: splitting the base sheet across the nine widgets its rules target (all depth 1-2 under `mw`), and emptying the root sheet by moving the main-window background out of QSS. It also disproves the previously-recorded idea that the confinement was merely "applied at the wrong point". Depth, not widget count, is the multiplier: 600 widgets flat = 11.9ms vs deeply nested = 123.3ms, non-linear. Consequences: previews and snapbacks do **identical** work (`_apply_stylesheets` has no `hover` gate on any of its work), and a settings dismiss with a preview showing blocks ~600ms before the slide starts vs ~1.2ms without. Live cost is **~436ms** (n=120 from the real app; the offscreen harness reads ~25% high, so quote 436 not 550). Cost tracks **visibility** — ~22% higher with the four heavy panels shown, at *identical* widget count — not transient content. **All three non-structural options are now dead**, each on a measurement: (A) splitting the sheet across its nine target widgets saves nothing since rule count is irrelevant; (F) emptying the root saves nothing since clearing costs the same as setting; (E) guarding redundant applies fires only 1-5×/session in a real log while the **existing** no-op guard already catches 44 at zero cost. The only remaining fixes are structural, and there are **two independent levers, not one**: reduce nesting DEPTH, and reduce how many widgets are VISIBLE at once (measured as a ~22% swing on its own). Both **connect to the Stats refactor** since Stats is a deep subtree that maps a lot of widgets simultaneously. A `hover` gate is warned against by `5cfe3a3` §2 (reverted regression). See NOTES.md 2026-08-02 (root-restyle entry) for the measurement tables, the corrected empty-sheet error, and the disproven explanations.
- **Backdrop-mode switch still restyles hidden panels (~390-555ms/click); skipping needs a deferred-open guard, and Stats needs its own perf refactor first** (2026-08-02) — `ThemeManager.apply_panel_alpha_pass` styles all seven panels regardless of visibility. Skipping the hidden ones would take a click to ~140ms (only `settings_panel` is visible when the control is used), but the deferred apply then races the user: switch mode → Esc → press a panel key. Requires a guard that **defers a panel open while a stylesheet is pending for that panel**; imperceptible everywhere except Stats, where 100-200ms is acceptable and beyond that "would feel like something is broken". A timeout-and-open-anyway fallback trades the stall for a race on a path where half-applied styling is a visible defect. All figures are one machine — computer speed, library size and **Stats size** (unbounded books in Day/Week/Month + period pages, no perf refactor yet) all scale it, so Stats' 105ms is not a fixed cost. A lazy/idle-timer variant additionally needs `_preload_paused()`-style gating or it reintroduces the mid-slide stutter recorded in `set_blur_selection`'s 2026-07-28 comment. **Deliberately deferred behind the Stats refactor.** See NOTES.md 2026-08-02.
- **Panel restyle cost is Qt subtree re-polish, and it drifts run-to-run on identical code** (2026-08-02) — building the stylesheet strings is 0.1ms; every remaining millisecond is `setStyleSheet` re-polishing widget subtrees (settings 134, stats 105, book_detail 45), so caching/memoising theme dicts cannot help — cost is proportional to widget count per panel. Separately, the same clicks measured ~555ms and later ~390ms with no code change, matching the 87ms→410ms post-launch step in the 2026-08-01 entry: **a second independent sighting, so treat any before/after figure on this path as valid only within one run.** Root cause of the drift unexplained. See NOTES.md 2026-08-02 and 2026-08-01.

## Stats / library UI

- **Closing Book Detail leaves the panel underneath with no focus owner** (2026-08-01) — `_on_book_detail_hidden` (`panels.py`) calls `_release_panel_focus(book_detail_panel)`, which clears focus but grants it to nobody. Book Detail is the one overlay that opens ON TOP of another (deliberately ungated by `is_overlay_open_or_committed`), and it took that panel's focus via `_claim_panel_focus` on open — so on dismiss the still-visible Stats/Tags/Library panel is left with no focus owner, violating the "exactly one widget owns focus" invariant. Consequence: `MainWindow._focus_allows_global_shortcuts()` sees `focusWidget()` as None and starts answering keys the open panel should own. Fix is a `_reclaim_underlay_focus()` in `_on_book_detail_hidden` using the `_book_detail_underlay` key the blur suspend/resume pair already tracks — Stats/Tags via `_claim_panel_focus`, Library via whatever its own `showEvent` grabs (it self-manages and is not routed through the shared helper, and `showEvent` won't re-fire since it was never hidden). Deliberately left out of the 2026-08-01 Book Detail blur change to keep that isolated; **to be picked up in the future pass on Stats keyboard navigation.** See CLAUDE.md "Keyboard focus ownership".
- **Tag list builds a real widget per tag, eagerly, on every refresh** (2026-08-01) — `TagManagerWidget._refresh_tag_list` calls `_build_tag_row` for every tag and `deleteLater()`s the previous set each time; each row is a `QWidget` with a layout, three `QLabel`s, `WA_StyledBackground`, `WA_Hover` and a cursor. At the 50-tag global cap that is ~200 widgets and imperceptible; it is why the cap can't simply be raised. The Library panel does the same job with `QAbstractListModel` + a delegate and holds no per-book widgets. Raising the cap means virtualizing first, then adding search/letter-jump navigation. **Not planned work** — see NOTES.md 2026-08-01 for the full accounting.
- **Constraining a lone stretch participant's height moves the whole block** (2026-08-01) — the Stats Day/Week/Month rows scroll area is its column's only `stretch=1` member, so it absorbs all leftover height. Constraining that height — `setFixedHeight` **or** `setMaximumHeight`, both tried, both reverted — withdraws it from the stretch, and `QVBoxLayout` then redistributes the freed pixels *around* the block, pushing the total label and short lists down from the top. Capping only works **paired** with an explicit `addStretch()` below the scroll area, giving the slack a home below the rows. Shipped that way in `_cap_rows_viewport` (7 rows when no Finished section; uncapped with one, where the section already consumes the remainder). Generalizes beyond Stats: any single-stretch column has this property. See SESSION.md 2026-08-01.
- **Row-boundary pixel is delivered to the parent, not the row — worked around, cause is Qt's** (2026-07-31, RESOLVED for Stats) — the last pixel of a flush-stacked widget goes to the parent under real input. Reproduced with six bare `QWidget`s and no layout engine (`tools/row_hittest_minimal.py --show --no-layout`); the control variant with real inter-row gaps routes every hit correctly. Not fixable in this codebase: the Stats lists work around it by having the rows container own the cursor and route those presses to the tracker's `hovered_row`. **Tags rows share the shape and are NOT worked around** — deliberate, their geometry is due for rework. See NOTES.md 2026-07-31 (later).
- **Blur freezes during a Stats scrollbar drag; the real fix is to shrink the grab region, not suspend the grab** (2026-07-31) — the shipped fix for the undraggable Stats scrollbars suspends the entire blur refresh for the length of a slider drag, so anything animating on its own (the chapter slider on a short chapter, a scrolling title) drifts out of sync with the live widget underneath until release, when a full-rect re-grab resolves it. The narrower fix, identified by Pryme: **exclude the scrollbar area from the Stats grab region entirely** — the top part of the panel already doesn't animate, and the animating elements (time labels, chapter label, chapter slider) sit outside the scrollbar area in most cases. The only element genuinely inside it is the Play button, which requires reaching EOF while Stats is open in blur mode to change appearance, and self-corrects on panel close. **Explicitly not a TODO item — no intention to implement while more important issues are outstanding.** See NOTES.md "Hiding a panel mid-drag destroys `QAbstractSlider`'s drag state" (2026-07-31).
- **List-mode elided multi-author: first segment unreachable when hover-expanded** (2026-07-06) — hover-invade only triggers/holds while the cursor is in the author zone `[mid, right)`, but an expanded elided author draws leftward past `mid`, so its FIRST name sits left of `mid` — moving there leaves the zone and collapses it (can't be clicked, and can't even be fully read). Accepted limitation, inherent to pre-existing invade geometry, not specific to the click-to-filter feature that exposed it; the first name stays clickable in the resting/partly-elided state. Fix would widen the invade hold-zone to the full expanded rect, which competes with the title's left-side expand zone when both are elided — deferred. Comment at `_list_author_layout`'s `expand_author`. See SESSION.md 2026-07-06 (List author click-to-filter).
- **List-mode row geometry depends on live `option.rect.width()`, which is not constant** (2026-07-06) — `BookDelegate._paint_list_row` reads `option.rect.width()` to derive `AVAILABLE`, but `setResizeMode(ResizeMode.Adjust)` + `ListMode` makes the row width track the live viewport (not a fixed `sizeHint`), so a paint mid-slide-in / pre-settle can differ → the same title elides in one paint and not another. Resting geometry is otherwise a pure function of `(book, option.rect, option.font)`; width is the only non-constant input. (The specific scrollbar-toggle case is now fixed for List AND 1-per-row via `_row_content_width`/`_row_stable_right`; this entry covers the residual mid-transition/pre-settle instability, still open.) See NOTES.md "List-mode title/author spacing" (orthogonal-instability section).
- **List-mode title→author spacing — unfixed after 3 reverted attempts** (2026-07-06) — the visible glyph gap is content-dependent (`reserve + title's left-align slack + author's right-align rect slack`) because title is left-aligned and author right-aligned; rect-boundary padding can't make it constant. Needs a glyph-extent-relative approach, not rect edges. Title-side wrong-font measurement WAS fixed (`d37507c`). See NOTES.md "List-mode title/author spacing".
- **Semi-transparent session history rows — investigation dead end, not pursued** (2026-06-10) — goal was matching the Tags panel's row transparency; abandoned because `QScrollArea`'s internal viewport resists QSS/`WA_*` transparency attempts. Current baseline (solid alternating colors) is accepted. Root structural issue: a shared `get_stats_stylesheet()` makes this kind of scoped QSS override fragile — a dedicated stylesheet function for `BookDetailPanel` was named as a possible path but not pursued. Grey area: also reads as a deferred polish feature, not purely structural. See NOTES.md "Semi-transparent session history rows — investigation dead end".
- **Screen drag 4K→1080p: cover scaling doesn't update without scroll** — needs `QWindow.screenChanged`. See CLAUDE.md "Pending / Known Debt".
- **MP3 natural sort (2 before 10)** — out of scope for v1. See CLAUDE.md "Pending / Known Debt".

## Error handling / robustness

- **Book switch state split on DB failure** — `_on_book_selected_from_library` (app.py:1449–1458) has no rollback if `db.update_last_played` raises mid-sequence; `current_file` can end up pointing at a book mpv isn't actually playing. Not a common failure mode. See NOTES.md "Book switch state split on DB failure".
- **`cover_path` can be an audio file path in an edge case** — only when thumbnail `img.save()` fails (disk full/permissions); `CoverLoaderWorker` then silently shows no cover rather than crashing. Accepted failure mode, no fix planned. See NOTES.md "cover_path can be an audio file path in edge case".
- **Known gaps — missing-file edge cases not yet exercised** (2026-06-08) — two scenarios identified but unverified: partial VT folder removal (some but not all multi-file book files deleted externally), and removable/network drive unmount mid-buffer (likely funnels through existing error handling, but timing/UX unconfirmed without real hardware). See NOTES.md "Known gaps — missing-file edge cases not yet exercised".
- **Config `balance` key has no bounds validation** — `config.set_balance()` has no clamp; a corrupted/manually-edited QSettings value could pass an out-of-range balance to mpv's audio filter silently. Fix: clamp `[-1.0, 1.0]` in `set_balance`, deferred to next config touch. See NOTES.md "Config — `balance` key has no bounds validation".
- **`upsert_cover` deletes the file before the DB row** — wrong order; if the DB delete fails, the DB still references a now-missing file (broken thumbnail). Correct order is DB-first. Address when cover panel is next touched. See NOTES.md "`upsert_cover` delete ordering — file before DB".
- **`_on_thumb_delete` doesn't check the file-delete return value** — a silent file-deletion failure leaves an orphaned file with no log. At minimum, log the failure. See NOTES.md "`_on_thumb_delete` does not check file delete return value".
